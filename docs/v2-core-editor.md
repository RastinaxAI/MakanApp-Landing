# STEP 2 — هستهٔ صفحه‌ساز در CMS موجود

## تغییر واقعی

Puck Core 0.23.0 به‌عنوان Canvas React انتخاب شد. سند ذخیره‌شده، قرارداد مستقل پروژه با `schema_version=2` است؛ خروجی داخلی Puck یا HTML آزاد در دیتابیس ذخیره نمی‌شود. همان Page، PageRevision، رسانه، Preview، انتشار، حساب‌ها و مجوزهای موجود استفاده می‌شوند. CMS یا Authentication دوم ساخته نشده است.

Home/Page می‌توانند سند جدید داشته باشند. صفحات قدیمی همچنان با Renderer قبلی نمایش داده می‌شوند؛ بازکردن آن‌ها در صفحه‌ساز، هر سکشن را به LegacySection قابل ویرایش تبدیل می‌کند. انتشار موجود تا عملیات صریح Publish باقی می‌ماند. تبدیل یا حذف دسته‌جمعی داده انجام نشده است.

Canvas دارای کانتینر و Grid تو‌در‌تو، درج و جابه‌جایی با Drag & Drop، ویرایش عنوان روی صفحه، انتخاب، تغییر عرض، Undo/Redo موتور و تنظیم Style پایه/تبلت/موبایل/Hover/Focus است. رجیستری ۲۵ نوع عنصر تعریف شده؛ آزمون کامل همهٔ ویجت‌ها و ابزارهای پیشرفته مربوط به STEP 3 است.

دکمه‌های جابه‌جایی و فهرست انتخاب المان مسیر قابل استفاده با صفحه‌کلید فراهم می‌کنند. پس از انتقال، انتخاب به همان المان دنبال می‌شود. تنظیمات و Draft در PostgreSQL ماندگارند؛ LocalStorage منبع ذخیرهٔ محتوا نیست.

## قرارداد و امنیت

- `PATCH /api/v1/admin/content/{id}` همان مسیر ذخیره است؛ سند جدید اختیاری است و محتواهای قدیمی معتبر می‌مانند.
- `POST /api/v1/admin/content/{id}/revisions/{revision}/restore` پیش‌نویس جدید ایجاد می‌کند؛ نسخهٔ منتشرشده و تاریخچه حذف نمی‌شوند.
- CSRF، RBAC، If-Match، Audit و حفاظت رسانه از سرویس موجود استفاده می‌کنند.
- API فقط ویجت‌ها و Styleهای ثبت‌شده را می‌پذیرد؛ تعداد/عمق درخت، IDها، واحدهای اندازه، رنگ‌ها، لینک و شناسهٔ آپارات محدود و اعتبارسنجی می‌شوند. Rich Text در سرور Sanitization می‌شود.
- فرم Canvas برای انتخاب و ویرایش است؛ فرم Public همان RequestForm و API واقعی دریافت درخواست را اجرا می‌کند.
- کتابخانهٔ Editor فقط در Admin با dynamic import بارگذاری می‌شود. CSS بدون import فونت خارجی استفاده شده است؛ CSP برای بارگیری فونت بیگانه تضعیف نشده است. iframe ویرایش فقط same-origin است.
- FAQ references در Renderer رعایت می‌شوند و صفحهٔ عمومی وابستگی‌های CMS لازم را دریافت می‌کند.

## آزمون و معیار پذیرش

سناریوی مرورگر Chromium موفق: ورود OTP → بارگذاری رسانه → ایجاد Page → Container → Heading/Image → جابه‌جایی → تنظیم فونت/رنگ/فاصله و اندازهٔ موبایل → افزودن DemoForm → Save → Refresh → Publish → ثبت درخواست واقعی و نمایش در CRM → Restore نسخهٔ اول به Draft بدون تغییر صفحهٔ منتشرشده.

۱۵ تست جدید Unit/Integration روی PostgreSQL مستقل موفق شدند: درخت تو‌در‌تو، Style موبایل، Sanitization، رد ورودی نامعتبر، حفاظت Draft/رسانه، مجوز و بازیابی نسخه. هر ۲۲۴ تست جامع API، ESLint، TypeScript و Build Production با Webpack موفق شدند. سناریوی کامل پذیرش روی خروجی Production در Chromium، Firefox و WebKit موفق شد (۳ تست، حدود ۱٫۹ دقیقه). شواهد در `docs/qa/v2-step2` هستند.

اجرای قابل تکرار API: `./scripts/test-backend.ps1 -Phase v2-step2`. تست Canvas: `playwright test --config playwright.v2.config.ts --project chromium` در `apps/web` با سرویس مستقل fixture روی 8100 و Web روی 3200. این دو سرویس به دیتابیس اصلی متصل نیستند. آماده‌سازی خودکار این تست‌ها در STEP 6 یکپارچه می‌شود.

## فایل‌ها و محدودیت مرحله

فایل‌های اصلی: `features/builder/*`، مسیر Admin Builder، schema/API/service CMS، Renderer مشترک، PublicPage، RevisionPanel، مسیر BFF، CSP، فرم ورود و تست‌ها. Migration جدیدی اجرا نشده است؛ Schema دیتابیس و Alembic head همان `0008_phone_otp` هستند.

این مرحله شامل کتابخانهٔ قالب پایدار، تنظیمات جهانی مشترک، Header/Footer builder و اتوماسیون CRM نیست؛ در مراحل بعدی اجرا می‌شوند. اجرای اولیهٔ هم‌زمان با تست سنگین دیتابیس، timeout سرویس داشت؛ اجرای نهایی پس از اتمام تست دیتابیس، در هر سه مرورگر موفق شد. شمار داده‌های دیتابیس اصلی: ۲۶ صفحهٔ منتشرشده، ۲۹ نسخه، صفر رسانه و لید، یک مدیر؛ همان شمار ممیزی.

منبع API موتور برای تکمیل ابزارهای مرحلهٔ بعد: [Puck headerActions](https://puckeditor.com/docs/api-reference/overrides/header-actions).
