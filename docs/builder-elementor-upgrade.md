# ارتقای تجربهٔ صفحه‌ساز

## مسئله و تغییر

در نسخهٔ قبلی، تصویر در دادهٔ هر تب ذخیره می‌شد اما رندر تب از آن استفاده نمی‌کرد. تب‌های مخاطبان صفحهٔ اصلی نیز به فهرست مخاطبان متصل بودند و تنظیمات بخش، محتوای درون تب را نشان نمی‌داد. کنترل‌های استایل و محتوا در یک فهرست طولانی قرار داشتند.

این اصلاح روی CMS، رجیستری Puck، رسانه‌ها و APIهای موجود انجام شده است. فایل `elementor.4.3.5.zip` صرفاً برای بررسی الگوی کنترل‌ها، تب‌های تنظیمات و ساختار ویرایش خوانده شد؛ فایل PHP یا JavaScript آن اجرا یا وارد پروژه نشد. پیاده‌سازی React است و افزونهٔ وردپرس Elementor در این برنامه نصب نشده است.

## امکانات

- کتابخانهٔ عناصر و تنظیمات در یک نوار کناری؛ انتخاب عنصر، پنل همان عنصر را باز می‌کند.
- تنظیمات «محتوا»، «استایل» و «پیشرفته»، همراه با دسترسی صفحه‌کلید.
- فهرست واضح موارد؛ افزودن، جابه‌جایی، تکثیر و حذف تا سقف موجود ۲۴ مورد.
- عنوان تب، تیتر داخل تب، عنوان کوتاه، متن ساده یا غنی، تصویر و پیوند مستقل.
- انتخاب تب روی بوم، همان تب را در پنل باز می‌کند؛ انتخاب مورد در پنل، پیش‌نمایش همان مورد را نمایش می‌دهد.
- نمایش تصویر هر تب در بوم، پیش‌نمایش خصوصی و خروجی عمومی.
- کتابخانهٔ تصویری صفحه‌بندی‌شده، جست‌وجو در صفحهٔ فعلی و بارگذاری مستقیم با API واقعی رسانه.
- انتخاب رسانه، پیش‌نمایش آن را نیز به‌روزرسانی می‌کند؛ تصویر خصوصی پیش از انتشار عمومی نمی‌شود.
- تب‌های مخاطبان صفحهٔ اصلی، تنظیمات محلی متن و تصویر دارند؛ برگه‌های مخاطبان تغییر نمی‌کنند.
- راهنمای محتوای مرجع و پیوند به برگه‌های مربوط برای عناصر متصل به فهرست امکانات، مخاطبان، پرسش‌ها و آموزش‌ها.
- حالت تمام‌صفحه و تنظیمات مستقل پایه، تبلت، موبایل، Hover و Focus.

## داده و سازگاری

جدول جدید، CMS دوم، CRM دوم یا احراز هویت جدید ایجاد نشده است. سند نسخهٔ ۲ با دو فیلد اختیاری `heading` و `eyebrow` در موارد گسترش یافته؛ اسناد قدیمی همچنان معتبرند. تصویر، HTML و پیوند از فیلدها و اعتبارسنجی‌های موجود استفاده می‌کنند. برای بخش مخاطبان، تنظیمات محلی در `props.items` همان عنصر نگهداری می‌شود؛ بدون تنظیم محلی، محتوای منتشرشدهٔ قبلی نمایش داده می‌شود. تغییر خودکار محتوای منتشرشده یا Migration دیتابیس لازم نیست.

ذخیره، کنترل هم‌زمانی، نسخه‌بندی، بازگردانی، انتشار، فرم واقعی دمو و CRM قبلی حفظ شده‌اند. این مرحله شامل واردکردن فایل‌های قالب Elementor یا پشتیبانی از افزونه‌های وردپرس نیست. داخل هر تب متن غنی و تصویر مستقل قابل ویرایش است؛ کانتینرهای تو‌در‌تو و عناصر عمومی از سازوکار موجود صفحه‌ساز استفاده می‌کنند.

## بررسی قابل اجرا

```powershell
npm run lint --workspace @makan/web
npm run typecheck --workspace @makan/web
apps/api/.venv/Scripts/python.exe -X utf8 scripts/run-v2-quality.py build --phase builder-elementor
apps/api/.venv/Scripts/python.exe -X utf8 scripts/run-v2-quality.py backend --phase builder-elementor
apps/api/.venv/Scripts/python.exe -X utf8 scripts/run-v2-quality.py browser --phase builder-elementor --spec all --project all
apps/api/.venv/Scripts/python.exe -X utf8 scripts/run-v2-quality.py browser --phase builder-elementor --spec builder --project all
apps/api/.venv/Scripts/python.exe -X utf8 scripts/run-v2-quality.py browser --phase builder-elementor --spec widgets --project all
```

تست‌های مرورگر از PostgreSQL آزمایشی و فرآیندهای اختصاصی استفاده می‌کنند؛ دادهٔ ساختگی به دیتابیس اصلی وارد نمی‌شود. نتیجهٔ نهایی و محدودیت‌های بررسی پس از اجرای آزمون‌ها در `docs/qa/builder-elementor` ثبت می‌شود.


## بازگشت نسخهٔ اجرا

قبل از جایگزینی محلی، imageهای قبلی با نام‌های `makan-editor-web-before:20261014`، `makan-editor-api-before:20261014` و `makan-editor-worker-before:20261014` نگه داشته شدند. مقایسهٔ محتوای دیتابیس و فایل‌های رسانه جداگانه انجام می‌شود؛ این مرحله هیچ Migration یا حذف/بازسازی جدول ندارد.

اگر بازگشت رابط لازم شد، می‌توان image قبلی وب را با همان سرویس وب اجرا کرد و API جدیدِ سازگار با داده‌های قدیمی را نگه داشت. بعد از ذخیرهٔ محتوایی با فیلدهای تازه، بازگشت API به نسخهٔ قبلی مستلزم بررسی نسخه‌های محتواست؛ بدون بررسی سازگاری، API قدیمی روی محتوای جدید اجرا نشود. Volumeهای دیتابیس، رسانه و تنظیمات نباید حذف شوند.


## نتیجهٔ نهایی — ۱۴ اکتبر ۲۰۲۶

- Build Production، ESLint، بررسی TypeScript و Ruff موفق شدند.
- ۲۴۷ تست سرور، شامل اعتبارسنجی و پاک‌سازی موارد تب، نگهداری رسانه، ذخیره/انتشار/بازیابی و احراز هویت و مجوزها، موفق شدند.
- مجموعهٔ کامل ۲۷ آزمون مرورگر، ۹ سناریو در هرکدام از Chromium، Firefox و WebKit، بدون شکست، حذف آزمون یا نتیجهٔ flaky موفق شد.
- سناریوی جدید: ساخت تب، تغییر متن و تیتر، بارگذاری مستقیم تصویر، جابه‌جایی و حذف مورد، ذخیره، بازکردن مجدد، پیش‌نمایش، انتشار، نمایش موبایل و ویرایش تب‌های مخاطبان صفحهٔ اصلی.
- رگرسیون بخش‌های آماده، واگرد/انجام دوباره، تغییر اندازه، سربرگ، رنگ‌های سراسری، CRM و فرم دمو، نمایش تمام ۲۷ ویجت و اسکرین‌شات‌های صفحات عمومی نیز بررسی شد.
- هر سه image برنامه ساخته و روی محیط محلی اجرا شدند؛ API، وب، PostgreSQL و نگهداری همگی `healthy` هستند.
- محتویات ۲۳ جدول تجاری و فایل‌های رسانه قبل/بعد دقیقاً برابر بودند: ۲۶ برگه و ۵۰ نسخهٔ موجود حفظ شدند. Schema همچنان ۴۰ جدول و Alembic همچنان `0009_demo_crm` است.
- ۹ مسیر اجرای محلی، شامل صفحات عمومی، ورود، آمادگی سرویس، پاسخ ۴۰۱ پنل بدون نشست و ۴۰۴ مسیر ناموجود، موفق بررسی شدند. فیلدهای تازه در OpenAPI همان API اجراشده نیز تأیید شدند.

در اولین راه‌اندازی، بارگذاری سرد API بعد از ساخت سنگین از مهلت اولیهٔ Health Check بیشتر طول کشید. مهلت اولیهٔ API و نگهداری در Compose توسعه به ۱۸۰ ثانیه افزایش یافت؛ این مهلت فقط خطاهای هنگام شروع را نادیده می‌گیرد و آماده‌شدن واقعی سرویس همچنان بررسی می‌شود. اجرای نهایی Compose و سلامت سرویس‌ها پس از این اصلاح تأیید شد.

نتایج قابل بررسی: `docs/qa/builder-elementor/verification.json`، `pytest.xml`، `browser.json`، `local-runtime.json`، `services.json`، `images.json`، لاگ Build و راه‌اندازی، و اسکرین‌شات‌های ویرایشگر دسکتاپ/موبایل. Lighthouse در این اصلاح دوباره اندازه‌گیری نشده است. بازطراحی عمومی سایت، نصب افزونه‌های WordPress، تغییر CRM یا احراز هویت در دامنهٔ این اصلاح نبود.
